# 机制分层查证

## 触发条件

适用：

- 用户问某个**具体系统**的机制："X 怎么工作""能不能 Y""这个功能怎么用""为什么 Z 是这样"
- 涉及具体产品（NandGame、DSH、某游戏、某编辑器）、具体语言的方言或指令集、具体框架
- 回答里会出现"它其实是……""它的做法是……"这类机制断言

不适用：

- 纯通用原理（"什么是栈""图灵机是什么"）
- 用户明确只要结论、不要机制

## 五步流程

### 1. 定层

先问自己：这是**平台 / 产品 / 语言 / 语法 / 运行时**哪一层的事？

不同层规则互相独立，不能跨层推导。产品层的设计约束推导不出语言层的语法，语言层的语义也决定不了产品层的 UI。

### 2. 定名

问题里的名词（栈、函数、程序、元件、宏、调用、寄存器）在该系统里具体指什么？

同名概念在不同系统里经常是完全不同的东西。动手回答前先把名词对齐。

### 3. 查官方

优先级：

1. 系统内置帮助面板、官方文档
2. 源码
3. 官方仓库的 issue / PR
4. 社区实测帖
5. 搜索引擎

禁止跳过这步直接用训练记忆。训练记忆里的"通用做法"经常不是该系统的实际机制。

### 4. 标不定

查不到的部分明确写「未验证」，禁止用"应该可以""大概是这样""通常都支持"糊过去。

不确定的语法、API、UI 路径，要么查证，要么标注，不能写成结论。

### 5. 给结论

区分证据强度并标注：

| 强度 | 含义 |
|---|---|
| 实测 | 自己跑过、看过输出 |
| 源码级 | 读过实现代码 |
| 结构推断 | 从多个证据推出来，未直接验证 |
| 猜测 | 没有证据，只是经验 |

阻塞性结论（"不能做""必须这样"）必须达到实测或源码级，否则标注前提未验证。

## 反例：2026-11 NandGame 事件

用户问 NandGame 的堆栈和函数调用。当时的错误：

| 我套用的机制 | 实际机制 | 混淆的层 |
|---|---|---|
| 标准汇编 CALL/RET | 只有 `A = 标签; JMP` | 语言 |
| 函数 + 返回地址栈 | macro 宏展开 | 复用 |
| 栈帧 / 寄存器调用约定 | SP 固定在 `RAM[0]` | 运行时 |
| Playground 程序 = 关卡程序 | 两套独立存储 | 产品 |
| 元件 = 程序 | Custom Components 与 Programs 是两种东西 | 对象 |
| `A = *A` 需要实测 | 语法明确支持 | 语法 |

每一条都是同一个错误：**用另一个系统的机制模型覆盖当前系统的机制**。

教训：先判"这是哪个系统的机制"，再判"这个机制长什么样"。跳过了第一步，后面全错。

## 自检

- [ ] 我说的是哪个系统的机制？
- [ ] 这个机制的官方定义我查了吗？
- [ ] 有没有把另一个系统的同名机制套过来？
- [ ] 跨系统的类比标注了"类比"吗？
- [ ] 不确定的部分标注了吗？
- [ ] 结论标注了证据强度吗？
