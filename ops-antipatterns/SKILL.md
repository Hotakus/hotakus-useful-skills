# 工程操作反模式（Ops Antipatterns）

本规范适用于任何项目的命令行与协作操作流程。当你要执行 git 分支/提交/推送/tag/worktree 操作、包版本发布、GitHub PR/Issue 协作时，先按本规范自查，避免用"想当然的绕路"替代标准做法。

## 1. 为什么需要

操作流程类错误有一个共同模式：**用未经验证的顾虑否定了标准做法**，或**把该确认的决策自己默认了**。它们不破坏代码，却会制造返工、造成多处不一致、污染公开协作面（PR / issue / 发布），甚至触发不可逆的远端动作。

遵守这些准则的取向是**先按标准走、遇到实际障碍再改道**，而不是预先假设障碍。

以下每条规则都给出一个**通用判据**（可当场验证自己是否违反）与**通用示例**（只用 git / npm / gh 等通用工具，任何项目都可直接类比）。

## 2. 标准路径优先

**先执行标准做法；未经验证的顾虑不得成为另造绕路的理由。**

**判据**：改道之前，必须能引用**一条实测报错**或**一条文档原文**；拿不出就不许改道。

**正确**：

```bash
# 先用标准的一步式命令：改版本号 + 生成提交 + 打 tag
$ npm version patch -m "chore(release): %s"
v1.2.3
# 结果：版本文件更新，自动生成提交 chore(release): 1.2.3，自动创建 tag v1.2.3。
# 实测：工作区存在未跟踪文件时，该命令依然成功。
```

**错误**：

```bash
# 反例：凭“未跟踪文件可能触发 clean 检查”的猜测，绕开标准命令
$ npm version patch --no-git-tag-version   # 绕过检查，只改版本号
$ npm run version                          # 手动补生成文件
$ git add package.json package-lock.json
$ git commit -m "chore(release): 1.2.3"    # 手动补提交
$ git tag v1.2.3                           # 手动补 tag
# 代价：4 步代替 1 步；且猜测不成立——标准命令本可一次成功。
```

## 3. 决策边界先确认

**默认值、初始状态、影响范围（跨版本 / 跨入口 / 跨平台）属必须确认的决策项。**

**判据**：凡涉及以上三者，动手前必须有一次**明确确认**（你向用户提问，或用户已明确指示）；不得默认为"保持现状"。

**正确**：

```text
动手前先问清楚：
1. 该开关/选项的默认值保持不变，还是改为另一种？
2. 该改动会影响哪些入口或构建目标（如 CLI / GUI、不同版本线）？需要全部同步吗？
```

**错误**：

```text
自行判断“默认值属实现细节，保持现状即可”
→ 按“保持现状”实现、验证、提交
→ 用户要求改为另一种默认值
→ 返工：重新实现 + 重新验证 + 重新提交；若已合并或发布，还要追加修复提交。
```

## 4. 最小动作

**只做被要求的事；不做与当前任务无关的动作。**

**判据**：每个动作都能对应到用户的**明确要求**；用户已表态"不用管"的领域不再产生任何新动作。

**正确**：

```text
用户：“这个问题先不管了”
→ 停止处理：不执行任何修复动作，也不补充调查。
```

**错误**：

```text
自动化流程产生了一个副作用（如把某条记录标记为已关闭）
→ 认定“这不符合要求”，属缺陷
→ 执行反操作（如重新打开）并开始排查原因
（用户已接受该结果；以上动作全部多余，且制造了额外噪音）
```

## 5. 先界定再动手

**动手前先界定作用域：涉及哪些入口、哪些版本线、哪些文件。**

**判据**：动手前能列出**受影响的全部位置**；列不全就先检索定位，再动手。

**正确**：

```bash
# 先定位同一功能的所有实现位置，再决定改动范围
$ rg -l "feature_name" src/
src/entry-a/index.ts
src/entry-b/index.ts
# 结论：两处都要改，避免只改一处造成行为不一致。
```

**错误**：

```text
只改 src/entry-a 就收工
→ src/entry-b 的等价实现未同步
→ 两处行为不一致 → 返工补齐。
```

## 7. 快速参考（反例 → 正例）

| 反例 | 正例 | 判据 |
|------|------|------|
| 猜测版本命令会因工作区不干净失败，改手动 commit + tag | 先直接跑一步式版本命令 | 有实测报错才改道 |
| 建分支前先查 worktree 占用、比对远端 | 直接 `git checkout -b <new> <base>` | 该步骤是否为达成目标的必要条件 |
| 把默认值默认为"保持现状"就动手 | 先确认默认值与影响范围 | 涉及默认值必须有一次确认 |
| 用户已接受的结果，仍去重新打开 / 补调查 | 停止处理，不做多余动作 | 每个动作都能对应到明确要求 |
| 发布通道未定，先做无关的账号/环境检查 | 流程确定后再做相关检查 | 检查是否当前决策所需 |
| 低价值决策也抛回用户选择 | 按既有惯例执行，仅在影响结果时提问 | 该决策是否改变最终结果 |
| 引用开发分支论证某个已发布版本的行为 | 切到对应 tag / 运行时版本再核验 | 来源是否与目标版本一致 |
| 只改一个位置就收工 | 先检索定位全部位置，再统一修改 | 能否列出全部受影响位置 |

## 8. 禁止事项

- 禁止用"可能不行"的未验证顾虑否定标准做法。
- 禁止把默认值 / 初始状态 / 影响范围当作实现细节自行决定。
- 禁止擅自处理用户已接受或已明示不处理的结果。
- 禁止做与当前任务无关的前置检查。
- 禁止把低价值决策抛回用户。
- 禁止在作用域（入口 / 版本线 / 文件）未界定前动手修改。

## 9. 自检要求

执行 git / 包发布 / PR-Issue 类操作前，逐项自检，如有未通过项，先修正再执行：

- [ ] 是否在用标准做法？若已改道，能否引用**一条实测报错或一条文档原文**？
- [ ] 是否涉及默认值 / 初始状态 / 影响范围？是否已有一次**明确确认**？
- [ ] 是否只做了被要求的事？有无无关动作或多余前置检查？
- [ ] 作用域（入口 / 版本线 / 文件）是否已界定，能否列出全部受影响位置？
