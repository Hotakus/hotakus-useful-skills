# Windows 桌面 GUI 控制调用纪律

适用于通过 MCP 桌面桥（windows-mcp 等）操作 Windows GUI 的场景。不绑定具体桥接层与工具命名。

## 1. 为什么需要

每次桌面操作都有硬成本：屏幕编码、UI 树遍历、模型解析图像。参数选错，单次调用差一个数量级；动作拆太碎，往返次数又把节省吃掉。这套纪律只做一件事——把每一步压到成本最低的那条路径上。

## 2. 截图必须带 region

**截图调用必须给 `region` 参数，禁止裸全屏截图。**

原因不是省 token，是后端选择。多数桥接层的截图实现按优先级链选后端（dxcam → mss → pillow），而 dxcam 在没给捕获矩形时会直接判定不可用，回落到最慢的 pillow。

实测数据（1920×1080 桌面）：

| 方式 | 后端 | 耗时 |
|------|------|------|
| 裸全屏 | pillow | 817 / 991 ms |
| region 340×140 | dxcam | 86 / 101 ms |

例外：第一次进入陌生界面、确实不知道区域时，允许一次全屏定位；之后一律 region。

**定位任务栏图标时只截图，禁止用 `Move` 悬停。**

悬停会弹出窗口缩略图，直接遮住主画面，还得再点空白处关掉，等于白付一次往返。任务栏图标的位置也不固定——打开的窗口数量或顺序一变，整排图标会整体平移，记固定坐标必然点错。

正确做法：切换窗口前先截一条任务栏区域（如 `region=[0, 1008, 1920, 1080]`），按图标形状认出目标，再乘 `Coordinate Scale` 换算成屏幕坐标，一次点击完成。

**正确**：

```text
Screenshot(region=[560, 380, 1360, 720])
```

**错误**：

```text
Screenshot()   // 不知道区域就裸调，落到最慢后端
```

## 3. 用文本树定位，不用图像定位

**Snapshot 用默认参数（`use_vision=false`），靠返回的 UI 树元素坐标定位。**

UI 树已经给出每个可交互元素的屏幕坐标和名称，足够了。打开图像只会让模型多绕一圈，还不一定比坐标准。

同时存在两套坐标，禁止混用：

| 坐标来源 | 是否已是屏幕坐标 | 用法 |
|---------|:---:|------|
| UI 树元素坐标，如 `(230,913)` | 是 | 直接传给 `loc` |
| 截图图像中的像素坐标 | 否 | 必须乘 `Coordinate Scale`（常见 1.3333） |

**错误**：把 UI 树坐标乘上缩放比，或者把图像像素坐标直接当屏幕坐标点击。

## 4. 等待界面用 WaitFor，不用截图轮询

**等待界面状态变化必须用 WaitFor，禁止"截图 → 判断 → 再截图"的循环。**

WaitFor 在单次调用内部轮询 UI 树，把 N 次截图压成 1 次调用。可用条件：`text_exists`、`active_window`、`element_exists`、`element_enabled`、`focused_element`。

**正确**：

```text
WaitFor(condition="text_exists", text="运行")
```

**错误**：

```text
Screenshot() → 判断 → Wait(1) → Screenshot() → 再判断
```

## 5. 动作返回成功即算数

**动作类工具（点击、输入、快捷键、滚动）返回成功，即视为已执行，不追加截图确认。**

反复验证是最大的往返浪费来源：每一步都截图，链条长度直接翻倍。

例外：任务本身就是结果性的（"程序开起来了没"、"文件存上了没"），在链条末尾验证一次。

**禁止用 `Move` + `Screenshot` 反复确认状态。**

`Move` 会把鼠标停在元素上，很多控件（任务栏、开始菜单磁贴、悬浮面板）在悬停时弹出额外 UI，既遮挡画面又可能改变布局。需要确认时直接截图，不要先移动指针。

## 6. 合并动作

**能一次调用完成的，不拆成多次。**

- 多个输入框：`MultiEdit` 一次填完，不用逐框 `Click` + `Type`
- 多个勾选：`MultiSelect` 一次选中
- 连续滚动：一次给够 `wheel_times`，不滚一下看一下

## 7. 控制权闸门按流程走

**`USER_CONTROL` 是安全闸门，不是报错。**

返回 `USER_CONTROL` 表示桌面控制权在用户手里，附带的 `wait_seconds` 是剩余等待时间。正确流程：

1. 调 `ControlStatus` 查当前状态
2. `state=user` 且 `wait_seconds>0` → 等它归零
3. `state=ready` → 重试原操作

**错误**：在 `USER_CONTROL` 状态下连续重试同一操作，把等待期刷成一片报错。

**操控结束必须主动释放控制权。**

任务做完后调 `ControlStatus(release=true)` 把桌面交还用户，再把应用窗口切回 DSH 并回报结果。长期占着控制权会让用户无法操作自己的电脑，也会让下一次 `USER_CONTROL` 判断失真。

## 8. 打开程序优先走专用工具

**桥接层提供了启动程序工具时，必须用它，不要退化到"快捷键 + 运行对话框 + 猜坐标"。**

优先级：

| 优先级 | 方式 | 说明 |
|:---:|------|------|
| 1 | `App(mode="launch_executable", executable=…)` | 按 exe 路径启动，可带参数与工作目录 |
| 2 | `App(mode="launch", name=…)` | 按开始菜单名启动 |
| 3 | `win+r` + 输入路径 + 回车 | 仅在前两者不可用时使用，对话框位置每次都要重新定位 |

## 9. 表单类操作：输入不等于提交

**向 GUI 表单填入内容后，必须显式触发提交动作，并在数据层验证结果。**

多数设置页是 dirty/save 模型：输入只改本地缓冲区，不点「保存 / 应用 / 确定」不会写回配置，也不会让运行时重载。输入框里显示有值，只证明字符进了输入框。

正确流程：

1. 动手填之前先扫一眼页面底部或顶部有没有「保存」「应用」按钮，记下它的位置和初始状态（通常是 `disabled` 灰色，有改动才变亮）
2. 填完 → 点提交按钮 → 等它从「保存中…」变回「保存」
3. 验证落在数据层：读配置文件确认字段已写入，或重新打开页面看值还在，或直接调用依赖该配置的功能看行为变没变

**错误**：

```text
Type(loc=…) → 截图看到框里有字 → 认为配置已生效
```

**正确**：

```text
Type(loc=…) → Click(保存按钮) → 读配置文件确认字段落盘
```

真实踩坑：某设置页填入 `198.18.0.0/15` 后截图确认输入框有值，但没点保存，后续功能仍按旧配置运行；直到重读配置文件才发现根本没写进去。

## 10. 禁止事项

- 禁止裸全屏截图（首次定位除外）
- 禁止用 `use_vision=true` 做元素定位
- 禁止用固定 `Wait(n)` 等界面稳定，用 WaitFor
- 禁止在 `USER_CONTROL` 状态下连续重试
- 禁止每个动作后截图确认
- 禁止把 UI 树坐标和图像像素坐标混用
- 禁止表单只填入不提交
- 禁止用 `Move` 悬停任务栏图标来定位（缩略图会遮挡主画面）
- 禁止用 `Move` + 截图反复确认状态
- 禁止操控结束后不释放控制权

## 11. 自检要求

执行桌面操作前自检：

- [ ] 这次截图给了 region 吗？
- [ ] 定位靠文本树坐标还是靠看图？
- [ ] 等界面用的是 WaitFor 还是 sleep + 截图？
- [ ] 打开程序走的是专用工具还是 win+r 兜底？
- [ ] 动作返回成功后，还要不要再截图确认？
- [ ] 坐标来源标清楚了吗（UI 树 / 图像像素）？
- [ ] 表单填完后点提交了吗？结果在数据层验证过了吗？
- [ ] 定位任务栏图标用的是截图而不是悬停吗？
- [ ] 动作成功后还在用 `Move` 确认吗？
- [ ] 结束前 `release` 控制权了吗？

出现违反以上任一项的操作，重新执行。
